日志配置
========

takler 的日志走一个统一的门面：代码用 ``get_logger(组件名)`` 获取
logger ，运维通过少数几个环境变量控制级别与去向，不需要改动代码。
本页说明级别、输出格式、落盘与轮转策略，以及审计记录的分流机制。
``takler-server`` 的常驻运行与日志文件配置示例见
:doc:`/operation/deployment` ；审计日志本身的字段与查询方法见
:doc:`/operation/audit` 。

组件名
------

每条记录都归属于一个**组件名** ，例如 ``server.scheduler`` 、
``server.checkpoint`` 、 ``server.auth`` 、 ``server.zombie`` 、
``client`` 、 ``core`` 。调用 ``get_logger()`` 时不给名字（或给空串）
会得到根组件 ``takler`` 。组件名原样出现在每条记录里，是排查时定位
日志来源的第一线索。

级别
----

级别从低到高共六级，配置的是**阈值** ：级别不低于阈值的记录才会输出。

.. list-table::
    :header-rows: 1
    :widths: 20 20 60

    * - 级别
      - 数值
      - 典型内容
    * - ``TRACE``
      - 5
      - 最细的诊断信息
    * - ``DEBUG``
      - 10
      - 调度与命令处理的细节
    * - ``INFO``
      - 20
      - 启动、停机、恢复等正常里程碑（**默认级别** ）
    * - ``WARNING``
      - 30
      - 配置回退、 zombie 处置、写失败降级
    * - ``ERROR``
      - 40
      - 单个 flow 或单个请求的处理失败
    * - ``CRITICAL``
      - 50
      - 触发干净停机的致命错误（见 :doc:`/operation/resilience` ）

阈值由环境变量 ``TAKLER_LOG_LEVEL`` 设置，大小写不敏感、忽略首尾空白。
取值无法识别时**不会报错** ：服务记一条指名该取值的 WARNING 并回退到
``INFO`` ；空串与纯空白视为未配置，同样落到 ``INFO`` 。低于阈值的日志
调用被直接抑制，不向调用方抛任何异常。

输出格式
--------

所有输出目标使用同一个固定布局，控制台与日志文件的内容逐字节一致：

.. code-block:: text

    2026-06-30T11:38:10.123+08:00 INFO server.scheduler scheduler shutting down...

四个字段依次为：带毫秒与 UTC 偏移的 ISO 8601 时间戳、级别名、组件名、
消息文本，以单个空格分隔。时间戳显式带时区偏移，跨时区对照日志时不
会产生歧义。

输出目标
--------

**控制台** ：默认开启，写到 stderr 。前台运行时这就是全部输出。

**日志文件** ：由环境变量 ``TAKLER_LOG_FILE`` 指定路径后启用，与控制台
并行输出、内容一致；父目录不存在时自动创建。文件无法创建或打开时
（权限、只读文件系统），服务向控制台记一条含路径与原因的 WARNING ，
跳过文件 sink 继续运行——日志落盘失败不阻止服务启动或运行。

``takler-server`` 在启动流程的**第一步** 配置日志（见
:doc:`/operation/deployment` 的启动顺序），此后的启动、命令处理与停机
记录都落到配置好的去向。配置过程本身失败时，服务回退到「控制台 +
INFO 」并记一条 WARNING ，启动继续。

轮转与保留
----------

轮转 (``rotation``) 与保留 (``retention``) 只是 ``takler.logging.configure()``
的 API 参数，**没有对应的环境变量**， ``takler-server`` 也不暴露它们——
服务日志默认不轮转。需要对服务日志做轮转时，用 logrotate 之类的外部
工具；嵌入 takler 的应用可以自行调用 ``configure(rotation=..., retention=...)``
：

* ``rotation`` ：字节数（整数或 ``"10 MB"`` 、 ``"512KB"`` 这样的尺寸串，
  单位 ``B`` / ``KB`` / ``MB`` / ``GB`` / ``TB`` ， 1024 进制），或时间间隔
  （ ``"1 day"`` 、 ``"30 minutes"`` 、 ``"1 hour"`` 、 ``"1 week"`` 、
  ``"midnight"`` ）
* ``retention`` ：保留的轮转文件份数（整数）；省略时全部保留。标准库
  后端只支持按份数保留，无法解析为份数的取值按「全部保留」处理

审计记录的分流
--------------

配置了审计文件（ ``TAKLER_AUDIT_FILE`` 或 ``connect.yaml`` 的
``security.audit_file`` ）后，日志子系统安装第三个 sink ，并按组件名
做**双向隔离** ：

* 组件名为 ``audit`` 的记录只进审计文件，控制台与常规日志文件都拒收
* 其他组件的记录不会混进审计文件

审计 sink 输出**不带任何前缀的裸消息** ——一条审计记录本身就是完整的
JSON 对象（自带 ``timestamp`` 键），加上时间戳前缀会让每行不再是合法
JSON 。审计文件由审计写入方在第一条记录时以 ``0600`` 预创建， sink
延迟到第一条记录才打开文件，因此不存在按进程 umask 创建的窗口，见
:doc:`/operation/audit` 。未配置审计文件时不安装审计 sink ，审计记录
随控制台与常规日志文件输出，以常规布局出现。

两个后端
--------

日志子系统有两个可互换的后端，每个进程在首次使用时选择一次、之后不变：

* 安装了可选依赖 **loguru** （ ``pip install takler[log]`` ）时使用
  loguru 后端
* 未安装时使用 Python 标准库 ``logging`` 后端（标准库没有 ``TRACE``
  级别，后端会注册数值 ``5`` 的自定义级别补齐）

两个后端输出的级别集、记录布局与组件归属完全一致，换后端不改变运维
看到的任何一行日志的格式；轮转与保留在两个后端上都可用（ loguru
原生支持，标准库后端映射到 ``RotatingFileHandler`` 与
``TimedRotatingFileHandler`` ）。

环境变量汇总
------------

.. list-table::
    :header-rows: 1
    :widths: 28 72

    * - 环境变量
      - 作用
    * - ``TAKLER_LOG_LEVEL``
      - 日志级别阈值，默认 ``INFO`` ；无法识别的取值记 WARNING 并回退
        ``INFO``
    * - ``TAKLER_LOG_FILE``
      - 常规日志文件路径，未配置时只有控制台输出
    * - ``TAKLER_AUDIT_FILE``
      - 审计日志文件路径，未配置时审计记录随常规目标输出，见
        :doc:`/operation/audit`

日志相关环境变量只有这三个：控制台开关、轮转与保留只能经
``configure()`` 的显式参数设置。每一项的取值优先级都是
**显式参数 > 环境变量 > 内置默认值** ，且逐项独立生效——只显式传
``audit_file`` 时，级别与日志文件仍可从环境变量取得。
``takler-server`` 正是这样做的：它只把解析出的审计文件路径显式传给
``configure()`` ，其余全部交给环境变量与默认值，因此上表就是服务日志
的全部配置面。

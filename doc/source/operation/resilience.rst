韧性与异常策略
==============

服务有两条异常边界：调度器主循环里**每个 flow 一条** ，网络服务里
**每个 RPC 处理器一条** 。意外异常撞到边界时怎么办，由异常策略
(``ExceptionPolicy``) 统一决定。本页说明两种策略、配置方式、按 flow
的隔离边界、主循环超时告警，以及致命错误如何触发干净停机。

两种策略
--------

.. list-table::
    :header-rows: 1
    :widths: 18 82

    * - 策略
      - 行为
    * - ``resilient``
      - **默认值** 。记下日志后恢复：调度器跳过出错的 flow 继续处理其余
        flow ；RPC 处理器向客户端返回错误响应。服务进程保持运行
    * - ``fail_fast``
      - 记下日志后触发**干净停机** ：服务走完与正常停机完全相同的关闭
        流程（包括写出最终快照），然后退出

无论哪种策略，异常都**先记日志** ：一条含操作标识（ flow 名或 RPC 方法
名加关键请求字段）、异常类型与消息的 ERROR ，附完整回溯； ``fail_fast``
随后再记一条 CRITICAL 说明正在按策略停机。日志先行，策略动作在后，
两种模式下诊断信息一样完整。

配置方式
--------

取值优先级为 **命令行选项** ``--exception-policy`` **> 环境变量**
``TAKLER_EXCEPTION_POLICY`` **> 内置默认** ``resilient`` ；该策略不在
``connect.yaml`` 中配置。取值大小写不敏感，连字符与下划线等价
（ ``fail-fast`` 、 ``FAIL_FAST`` 、 ``fail_fast`` 均可），空白视为未
配置。无法识别的取值**不会报错** ：记一条指名该取值的 WARNING 并回退到
``resilient`` ——配置错误永远不会让服务变得更脆弱。

按 flow 的异常隔离
------------------

调度器主循环的每个周期遍历所有 flow ，**每个 flow 在自己的异常边界内**
处理（更新日历加依赖求解，未 begin 的 flow 整个跳过）：

* 一个 flow 抛出意外异常，只影响这个 flow 的本次处理——记 ERROR 后
  跳过它，同一周期的其余 flow 照常处理，主循环继续运行
* 下一个周期会再次处理该 flow ：错误若是一次性的（共享文件系统抖动
  等），下个周期自愈；若持续存在，则每个周期一条 ERROR ，日志里
  一眼能看出是哪个 flow 、什么异常
* 遍历基于 flow 表的快照进行，处理过程中 flow 的增删不会让本轮遍历
  本身出错

这就是「某个 flow 出错时其余 flow 不受影响」的机制：故障的半径是一个
flow 的一个周期，而不是整个服务。

RPC 边界的处置
--------------

每个 RPC 处理器（命令与查询）在同一层边界内执行调度器操作。撞到意外
异常时：

* ``resilient`` ：返回该处理器响应类型的错误表示——命令处理器返回
  非零 ``flag`` 的响应（ ``flag`` 携带按异常类型分类的错误码），查询
  处理器返回其错误表示；客户端按既有错误路径处理，服务继续运行
* ``fail_fast`` ：触发干净停机，但**先把错误响应返回给客户端** ——
  客户端看到的仍是一次正常的错误应答，而不是连接被掐断

两种模式下，运维命令的审计记录都照常写出（ ``outcome`` 为 ``error`` ），
见 :doc:`/operation/audit` 。

主循环超时告警
--------------

主循环每个周期的处理耗时若超过主循环间隔（内置 ``10`` 秒），服务记
一条 WARNING ，同时给出实际耗时与间隔两个数值，并**立即开始下一个
周期**（不补睡）。这条 WARNING 意味着 flow 规模或单周期工作量已经
超过间隔预算，是考虑拆分 flow 或排查个别 flow 处理慢的信号，而不是
故障——调度节奏仍然保持，只是没有空闲时间。

致命错误与干净停机
------------------

``fail_fast`` 下，调度器或网络服务触发停机时**不是就地退出进程** ，
而是置起一个共享的致命错误事件。服务的 ``run()`` 同时等待调度器任务
结束与该事件，任一先发生都进入**同一条干净关闭流程** ——与收到
``SIGTERM`` 的正常停机（见 :doc:`/operation/deployment` 的停机一节）
完全共用：停网络服务、停调度器，最后由检查点管理器写出**最终快照** 。
关闭流程有守卫，两条路径同时到达也只执行一次。

因此 ``fail_fast`` 停机不丢状态：下次启动从最终快照恢复，在途任务
保持 submitted / active （见 :doc:`/operation/checkpoint` ）。

何时选 fail_fast
----------------

``resilient`` 适合生产：一个 flow 的定义问题（例如自定义 Task 子类的
``resolve_dependencies`` 抛错）不该拖垮同服务的其他 flow ，错误响应
也让客户端按既有路径处理失败。

以下场合考虑 ``fail_fast`` ：

* **开发与调试** ：让第一个意外异常直接停机，配合日志里的完整回溯
  定位问题，而不是让服务带着错误继续跑
* **「意外异常即状态不可信」的部署** ：宁愿立刻从快照重启，也不愿
  继续接受命令。因为有检查点恢复兜底（见
  :doc:`/operation/checkpoint` ），重启代价很低——配合 systemd 的
  ``Restart=on-failure`` 即可获得自动拉起
* **升级验证窗口** ：升级后先以 ``fail_fast`` 运行一段时间，把潜伏
  的兼容性问题变成立即可见的停机，而不是分散在各 flow 的周期
  ERROR 里

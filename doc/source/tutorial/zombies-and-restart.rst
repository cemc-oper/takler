僵尸与重启恢复
================

本节介绍 Takler 的两个可靠性机制：

* **僵尸检测** ：识别并处置「不属于任务当前运行实例」的上报，防止一个
  已经被重排队的任务的旧作业污染新一轮运行
* **检查点 (checkpoint)** ：服务周期性保存快照，进程被杀掉后重启可以从
  快照恢复，正在运行的作业不受影响

两个机制可以亲手复现，本节继续使用 :doc:`controlling-the-flow` 一节的
示例工作流。

僵尸作业 (zombie)
--------------------

**什么是僵尸** 。任务脚本通过 child 命令（``init`` 、 ``complete`` 、
``abort`` 、 ``event`` 、 ``meter`` ）向服务上报状态。典型的僵尸场景：
任务 ``t1`` 正在运行，你对它执行了 ``requeue`` ——服务端 ``t1`` 回到
``queued`` 并很快被重新提交（新一轮运行开始），但**旧作业还在跑**。当
旧作业最后调用 ``complete`` 上报时，这条上报就属于已经不存在的运行
实例：如果放行它，新一轮运行的状态就会被旧作业篡改。

**try_no 与作业口令** 。服务靠两组运行实例标识区分新旧作业：

* 每次提交作业，任务的 ``try_no`` 加 1，作业脚本文件也随之编号
  （``t1.job1`` 、 ``t1.job2`` ……）；``requeue`` 把 ``try_no`` 清零
* 每次提交同时生成一个新的**作业口令** (job password)，通过作业脚本中的
  ``TAKLER_PASS`` 环境变量传给 child 命令；``requeue`` 同样将其清空

**判定条件** 。每条 child 命令在写入任何状态之前先过三道检查（命中
即视为僵尸）：

* ``Z1`` ：命令携带的口令与任务当前口令不符（或任务根本没有口令）。
  只在服务端开启鉴权 (``auth_mode: enabled``) 时检查
* ``Z2`` ：任务当前状态不是 ``submitted`` 也不是 ``active`` ——
  服务端没有正在等它上报的运行实例。``requeue`` 场景主要靠这条挡住
* ``Z3`` ：``init`` 命令携带的作业号与已记录的当前作业号不同——
  两个作业都声称自己拥有这次运行

**处置策略** 。命中僵尸条件的命令按 ``zombie_policy`` 配置处置：

* ``fail`` （默认）：拒绝，任务状态保持不变，客户端收到 ``ZombieError``
  报错并以非零码退出
* ``fob`` ：丢弃但回答成功，客户端无从察觉（服务端日志仍有记录）
* ``adopt`` ：接受上报，并把口令接管为命令携带的口令

无论哪种策略，每次处置都会在服务日志留下一条 WARNING，写明节点路径、
命令名、命中的条件与当前状态。策略与鉴权的配置方式见
:doc:`/operation/security` 。

**动手观察一次僵尸拒绝** 。为了让作业运行足够久，先临时在
**task1.takler** 中加一行 ``sleep 300`` ，然后：

1. 启动服务并 ``begin`` ，等 ``t1`` 进入 ``active``
2. 执行 ``takler-client-py requeue /test/t1`` ， ``t1`` 回到
   ``queued`` （旧作业仍在运行）
3. 在旧作业的 ``sleep`` 结束、调用 ``complete`` 时，服务端日志出现：

   .. code-block::

       WARNING ... zombie complete on /test/t1: hit Z2, status is queued, applying policy fail

   旧作业一侧的 child 命令报错并以非零码退出，新一轮运行的状态不受
   影响

也可以不启动作业直接模拟一条「过时上报」：在 ``t1`` 处于 ``queued``
时手动执行 ``takler-client-py complete --node-path /test/t1`` ，同样
命中 ``Z2`` 被拒绝。

.. note::

    默认部署不开启鉴权，此时不检查 ``Z1`` ：如果旧作业的上报恰好赶在
    新一轮运行提交之后到达（任务已是 ``submitted`` 状态），没有口令
    校验就识别不出它是旧实例。生产环境请参考 :doc:`/operation/security`
    开启 ``auth_mode: enabled`` 。

重启恢复 (checkpoint)
--------------------------

**快照** 。运行中的服务把整棵节点树周期性写入检查点文件（默认
``takler.check`` ，位于服务进程的工作目录，默认每 120 秒一次）；正常
退出时会再写最后一次。写入是原子的（临时文件 + 重命名），并同时维护
一个备份文件 ``takler.check.b`` 。快照保存节点状态、 ``suspended``
标记、事件与标尺取值、限额占用、repeat 当前值、时间依赖的 ``free``
闩锁、任务的 ``task_id`` / ``try_no`` / 中止原因、flow 的 begun 标记与
逻辑日历，以及**在途任务** （ ``submitted`` / ``active`` ）的作业口令
——因此文件权限被固定为仅属主可读写 (``0600``)。

**恢复** 。服务启动时按 ``takler.check`` → ``takler.check.b`` → 空
工作流的顺序回退恢复。关键是：恢复出的 ``submitted`` / ``active``
任务**保持原状，不会重新提交作业**——它们对应的作业还在计算节点上
跑着，重启只是让服务重新开始接受它们的上报（口令也从快照还原，
zombie 检查照常通过）。

**动手观察一次重启恢复** ：

1. 沿用上面带 ``sleep 300`` 的工作流，启动服务、 ``begin`` ，等
   ``t1`` 进入 ``active``
2. 等待至少一个快照周期（默认 120 秒；确认工作目录下出现
   ``takler.check`` ），然后用 ``kill -9`` 杀掉服务进程——模拟宕机，
   正常退出的收尾快照不会执行
3. 重新运行 **test.py** 启动服务，日志中会出现：

   .. code-block::

       INFO ... restored 1 flow(s) and 4 node(s) from checkpoint file takler.check.
       INFO ... recovered the job password of 1 task(s) from checkpoint file takler.check.

4. ``show`` 查看： ``t1`` 仍是 ``active`` 而不是被重新排队；
   旧作业的 ``sleep`` 结束后上报 ``complete`` ，服务正常接受，
   工作流继续向下走

.. note::

    重启后服务监听的地址或端口如果与快照中记录的不同，且快照里还有
    在途任务，那些任务作业脚本里写死的是旧地址，它们的上报会连不上
    新服务——服务启动时会对这种情况记录 ERROR 并列出受影响的任务。
    恢复在途任务时请保持地址端口不变。

练习
-----

1. 按本节步骤复现一次 ``Z2`` 僵尸拒绝，在服务日志中找到对应的
   WARNING 记录
2. 查看某次运行生成的 **t1.job1** 作业脚本，找到 ``TAKLER_PASS``
   环境变量；requeue 后再次运行，对比两次口令不同
3. 把快照周期调短（``connect.yaml`` 的 ``checkpoint.interval`` ，
   最短 10 秒），复现一次 ``kill -9`` 后的恢复
4. 删除 ``takler.check`` 但保留 ``takler.check.b`` ，重启服务，
   确认从备份快照恢复
